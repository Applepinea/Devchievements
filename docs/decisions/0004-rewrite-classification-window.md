# ADR-0004：Amend / Rebase 的分类等待窗口

- **状态**：**Accepted（数值为 Provisional，需跨版本复测）**
- **日期**：2026-11-16
- **相关规范章节**：§9.6、§9.7、§30.3
- **证据**：[git-behavior-experiments.md](../development/git-behavior-experiments.md) §2.3、§2.4

---

## 背景

规范 §9.6 定义了一套 Amend / Rebase 分类策略，其中窗口默认 **300 ms**，并要求
「以 Phase 0 实验结果由 ADR 调整」。

核心问题：post-commit 触发时，Helper 往往**还不知道**这次提交是不是被 rewrite 的对象；
post-rewrite 稍后才到，携带 old→new 映射。

---

## 实测数据

| 场景 | post-rewrite 相对上一 post-commit 的延迟 |
| --- | ---: |
| Amend | **436 ms** |
| Amend 后立即连续 Commit | **440 ms** |
| Rebase（2 个提交） | **452 ms** |

Git 2.54.0 / Windows 11 / 40 次基准下，单次 `git%% 调用约 33–37 ms，
空原生进程约 9 ms。本延迟包含 post-commit 自身工作时间（探针约 330 ms）。

### 另一个决定性发现

**交互式 rebase 的 reword 完全不触发 post-rewrite**（实验 §2.4）。
所以「等窗口就能等到 post-rewrite」这个假设**本身不成立**。

---

## 决策

### 1. 窗口默认值调整为 **800 ms**

理由：
- 实测上界 452 ms；
- 加上探针自身耗时造成的测量偏高，留约 1.7 倍余量；
- 800 ms 仍远小于规范「超过 10 分钟才算陈旧」的阈值，不影响新鲜度策略；
- **明确标注为 Provisional**：只在 Git 2.54.0 / Windows 11 上测得，跨版本分布未知。

> 为什么不取 500 ms：实测已到 452 ms，仅 10% 余量，任何稍慢的机器都会超时。
> 为什么不取 2000 ms：窗口越长，「普通 commit 被误判成 rewrite」的窗口也越长，
> 且会推迟通知的可发出时间。

### 2. 窗口**不是**唯一分类手段，也不是兜底保证

分类优先级（对应 §9.6 第 1–6 条）：

1. **post-commit 当场可判定**（不等窗口）：
   - reflog 消息为 `cherry-pick: …%% → Cherry-pick
   - tree 与父提交相同 → Empty Commit（排除）
   - 父提交数 ≥ 2 → Merge Commit（不计入普通 Commit）
   - reflog 消息为 `commit (amend): …%% → **初步**判定 Amend（仍需 post-rewrite 提供 old SHA）
2. **无法当场判定** → 标记 `pending_rewrite_classification%% 并持久化，**暂不产生最终通知意图**。
3. 窗口内 post-rewrite 到达 → 按映射关联。
4. 窗口超时 → 按普通 Commit 处理。
5. 迟到的 post-rewrite → **只修正统计投影**并写诊断日志，**不撤回已发出的通知**（§9.6 第 6 条）。

### 3. 交互式 rebase 的已知局限（必须写进用户文档）

因为 reword **不会**触发 post-rewrite，产品**无法可靠区分**「交互式 reword」与「新提交」。
后果：交互式 reword 可能被计为一次新提交。

缓解：
- 若 post-commit 的 reflog 消息匹配 `rebase (%%)%% 前缀，标记为 `rewrite_suspected%%%%，
  在诊断日志中记录；
- 但**不得**据此直接排除计数——那会造成漏计。
- 在文档中明确声明该局限，而不是假装解决。

### 4. 顺序无关性要求不变

§9.6 第 7 条要求「两个 Hook 无论谁先到达，最终统计结果必须一致」。
本实验**只在正常顺序**（post-commit 先于 post-rewrite）下观察，**未**测试乱序到达。
Phase 1 必须用属性测试覆盖乱序。

---

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 保持 300 ms | 无改动 | **实测必然超时**，Amend/Rebase 全部误分类 | 否 |
| 800 ms（采用） | 覆盖实测上界且有余量 | Provisional，跨版本未知 | **采用** |
| 2000 ms | 更保险 | 通知延迟明显；误分类窗口变长 | 否 |
| 不用窗口，完全依赖 post-rewrite | 逻辑简单 | 交互式 reword 永远等不到；会让普通提交延迟到窗口结束 | 否 |
| 不用窗口，全部立即判为普通提交 | 零延迟 | 违反 §9.6「不得先发出不可撤销的错误通知」 | 否 |

---

## 后果

- Amend / Rebase 的通知会推迟最多 800 ms，这是**有意付出的代价**，
  换取「不发出不可撤销的错误成就通知」（§9.6 第 8 条）。
- 该延迟**不计入** §44.1 的「Commit 到通知 p95 < 500 ms」预算，
  因为规范 §9.6 第 9 条明确「延迟目标只针对已分类事件，不含等待窗口」。
- 必须提供可配置项，并在诊断页暴露「窗口超时率」。

---

## 复查计划

跨 Git 版本实验（ADR-0003 补齐时）同时采集窗口延迟分布；
若在任一目标版本上出现 > 800 ms，重新评估并新开 ADR。
