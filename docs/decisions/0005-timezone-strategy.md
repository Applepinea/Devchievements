# ADR-0005：时区策略

- **状态**：**Accepted（技术选型）/ 具体实现待 Phase 1**
- **日期**：2026-11-16
- **相关规范章节**：§12、§11.2、§13.4、§31.2
- **证据**：本机 §12 相关字段已可用（见下），**尚无属性测试**

---

## 背景

规范 §12 定义了较严格的时区与日期语义：

- `local_date%% 在**事件入库时**按「事件时间 + 当时配置的 IANA 时区 + 当时的日界线」计算并**固定保存**；
- 之后修改系统时区或跨时区旅行，**不改变**既有事件的 `local_date%%；
- 日界线默认 00:00，可配置（如 04:00）；
- 夏令时导致日界线落在不存在/重复的本地时间时，用**时区库的标准解析规则**并需测试覆盖；
- 修改时区或日界线时，必须询问用户是否重算历史，**不得无提示改变**既有统计；
- 历史导入默认用**用户配置的 IANA 时区**（而非提交记录的偏移）计算 `local_date%%，
  原始偏移保存在 payload 中；
- Phase 1 增加属性测试：对任意事件序列与时区切换，`local_date%% 确定且不随重放改变；
  同一事件重复入库结果不变。

---

## 决策

### 1. 时区数据库：IANA TZDB，随应用打包，不依赖操作系统

**理由**：操作系统时区数据库会随系统更新变化。若依赖系统库，
同一事件在不同时间重算可能得到不同结果，**违反「重放不变」要求**。
因此必须把 TZDB 打进二进制，并在版本中记录 TZDB 版本。

### 2. Rust 侧实现：`jiff%%（含 `jiff-tzdb%%）

- 纯 Rust、无 C 依赖、可编译到 wasm32（浏览器侧复用同一逻辑的前提）；
- 自带 TZDB，满足「不依赖系统库」；
- 正确处理 DST 的不存在/重复本地时间。

> 注：Phase 0 已观察到 `jiff%% 在本机 GNU 目标下**构建失败**（构建脚本调用 `dlltool%% 时
> `CreateProcess%% 失败，属沙箱限制）。这一条**必须在 ADR-0001 的 spike 中复测**；
> 若最终无法在目标环境构建，需换库并更新本 ADR，**不得**为了沿用本决策而绕过。

### 3. 数据模型

每条事件保存：`occurred_at%%（UTC 毫秒）、`timezone%%（当时使用的 IANA 名称）、
`date_policy%%（当时的日界线，分钟）、`local_date%%（入库时算定，冻结）。
**`local_date%% 一旦写入永不在原记录上重算**；重算只能产生新的投影版本，并记录
「使用了哪个时区/日界线版本」和触发原因。

### 4. 重算策略

- 改时区 / 改日界线 → **必须弹窗询问**用户是否重算历史投影（§12）。
- 重算**不删除**原始 `local_date%% 字段，而是写入新的投影并标记来源，
  以便审计「这次统计为什么变了」。
- 历史导入：默认用当前配置的 IANA 时区 + 当前日界线；提供「按提交记录的时区」显式选项。

### 5. 日界线语义

`local_date = date(instant_in_zone) - (1 day if local_time < day_start else 0)%%。
日界线为 04:00 时，00:00–03:59 的事件归属**前一天**（§12 明确要求）。
DST 处理交给时区库的标准解析。

### 6. Engine 契约

Engine **不得**自己算时区：通过注入的 `TimezoneProvider%% 获取
（已在 `crates/core/src/context.rs%% 定义 `canonicalize%% 与 `local_date%% 两个方法）。
这样 Golden Tests 可以注入固定时区与固定日界线。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 系统时区库（`chrono-tz%% 用系统数据） | 简单 | 结果随系统更新变化，违反「重放不变」 | 否 |
| `chrono%% + `chrono-tz%%（内置 TZDB） | 生态成熟 | TZDB 打包方式与更新节奏需自管；wasm 支持需验证 | 备选 |
| **`jiff%% + `jiff-tzdb%%** | 纯 Rust、自带 TZDB、DST 处理正确、可 wasm | 本机 GNU 目标构建受阻（待复测） | **采用（待复测）** |
| 自己实现时区 | 完全可控 | 极高风险，DST 边界几乎必然出错 | 否 |

---

## 后果

- 数据库需要多存 3 个字段（`timezone%%、`date_policy%%、`local_date%%），
  并在事件表上建索引以支持按日统计。
- 必须记录 **TZDB 版本**；TZDB 升级本身也可能改变历史重算结果，
  因此升级 TZDB **不得**触发自动重算。
- 变更时区/日界线是**用户确认边界**内的操作（§46：「改变核心统计规则」）。
