# ADR-0002：Git Hook Helper 的实现方案

- **状态**：**Accepted**
- **日期**：2026-11-16
- **决策者**：Phase 0 实施方（待用户确认）
- **相关规范章节**：§9.5、§9.2、§44.1、§44.4、§30.2
- **证据**：[git-behavior-experiments.md](../development/git-behavior-experiments.md) §3

---

## 背景

规范 §9.5 要求：在三种 Helper 实现方案中**以 Phase 0 实测的 Hook 耗时为依据**做决策：

- **A**：调用 `git%% 命令
- **B**：链接 `gix%% / `git2%% 库
- **C**：直接读取 `.git%% 文件

同时受两条硬预算约束：

| 约束 | 值 | 出处 |
| --- | ---: | --- |
| Hook p95 执行时间目标 | < 50 ms | §44.1 |
| Hook 硬超时 | 200 ms（可配置） | §9.2 |

Helper 每次需要采集约 17 项事实（SHA、parents、tree、分支、author/committer 四人次+时间、subject、reflog 尾部等）。

---

## 决策

**采用方案 C：直接读取 `.git%% 的 Rust Helper（零外部 crate 依赖），
并辅以极少量必要的 `git%% 调用（仅在 C 无法覆盖的场景）。**

---

## 实测证据

同仓库、同批事实、各 40 次样本：

| 方案 | min | p50 | p95 | max | 判定 |
| --- | ---: | ---: | ---: | ---: | --- |
| A　单次 git 调用（最省的外派） | 33.95 ms | 35.47 ms | 38.34 ms | 45.33 ms | 接近上限 |
| A'　11 次 git 调用（朴素外派） | 369.15 ms | 393.78 ms | 428.26 ms | 485.62 ms | **违反硬超时** |
| B　链接 gix / git2 | — | — | — | — | **本机无法构建** |
| C　直接读 `.git%%（1 个进程） | 9.05 ms | 10.35 ms | 12.53 ms | 70.35 ms | **达标且余量大** |

### 为什么 A 也不行

即便把 17 次调用压成**一次** `git log%%（理论最省的外派形态），p95 仍是 38.34 ms，
已经吃掉 50 ms 预算的 **77%**，且 max 达 45.33 ms。任何额外工作（IPC、Spool、序列化）都会击穿预算。
而实际需要的字段无法用单次 `git%% 调用全部拿到（还缺 reflog、`.git%% 目录、commondir 等）。

### 为什么 B 没被选中

**B 不是被数据否定的，是被环境否定的**：

- `gix 0.74%% 在本机 **GNU 目标下无法构建**：其依赖链中的 `jiff%% 构建脚本调用
  `dlltool.exe%% 时报 `CreateProcess%% 失败（沙箱限制），与代码无关。
- 因此 **B 的耗时没有实测数据**，本 ADR 不对 B 的优劣下结论。

规范 §0.1 第 9 条要求「当前环境无法验证的能力一律标记为 Platform Unverified」，
故 B 记为 **未验证**。若后续在可构建 gix 的环境中测得 B 明显优于 C，
应新开 ADR 取代本 ADR，而不是直接改本文件。

---

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A　调 git 命令 | 语义最权威；不依赖实现细节 | 每次 ~33 ms，17 次即 ~600 ms；**必然违反 200 ms 硬超时** | 仅在 C 无法覆盖时按需少量使用 |
| A'　单次批量 git | 比 A 便宜 | 仍占 77% 的 50 ms 预算；字段不全 | 否 |
| B　链接 gix / git2 | 语义权威 + 免进程 | **本机无法构建，无数据**；增加二进制体积与安全面 | 未验证，保留为候选 |
| C　直读 `.git%% | 10 ms；零依赖；完全可控 | 需自行处理 packfile、SHA-256 等边界 | **采用** |

---

## 后果

### 正面

- Hook 从 672 ms（朴素外派）降到 **12.5 ms p95**，从**必然违反硬超时**变为**优于目标 4 倍**。
- 零外部 crate 依赖：不引入 gix 编译链，不受本机工具链限制影响，二进制小。
- 完全可测：可以在 Golden Tests 里用固定仓库目录直接验证解析结果。

### 负面 / 代价

- **必须自己实现并长期维护**：zlib inflate、commit/tree 解析、ref 解析、packed-refs。
  Phase 0 的 spike 已实现 loose object + 完整 inflate（stored / fixed / dynamic Huffman）。
- **packfile 尚未支持**：spike 只读 loose object。`git gc%% / `git repack%% 之后对象进入 packfile，
  此时 C 会失败。**Phase 1 必须补齐 packfile + delta 解析，或在此场景回退到 A。**
- **SHA-256 仓库未支持**（Git 2.29+ 可选特性）。
- **自研解析的正确性风险高于调用 git**：因此 **必须有 Golden Tests 对照 `git%% 的输出**，
  不允许「看起来对」就上线。

### 引入的新风险

- 若 packfile 支持不完整，Helper 会在仓库被 gc 后**静默失败**。
  缓解：**失败必须被诊断日志记录**，并且**回退路径明确**（回退到 A 的少量调用），
  绝不允许「读不到就当没发生」。

---

## 明确的回退策略

| 场景 | 行为 |
| --- | --- |
| loose object 可读 | 走 C |
| 对象在 packfile | **Phase 1 前**：回退到 1 次 `git log -1 --pretty=...%%（约 35 ms，仍在预算内） |
| 任何解析失败 | 记录诊断 + 回退到 A；**不得**静默丢弃事件 |
| 平台不支持（如 SHA-256） | 明确报错并降级，不得假装成功 |

---

## 复查计划

Phase 1 结束时，若已实现 packfile 支持，用 Golden Tests 对照 `git%% 输出复测；
若届时 B 能在 CI 中构建，补测 B 并与本 ADR 的数据对比，需要时新开 ADR 取代。
